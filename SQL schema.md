# SQL Schema Guide (AI-readable)

## Purpose and source

This file is the compact, human- and AI-readable map of the MySQL schema used by the **HighEducation / KSS** application. Read this guide first when answering project questions; consult the original SQL only when exact DDL, a migration operation, or database-specific behavior needs to be verified.

The schema below is transcribed from the project SQL exports: `PInventory/Dump20261016` (the CSR workflow scripts identified by the project owner) and `HighEducation/Dump20261016 (1)` (scholarship, organization, and user tables). The CSR scripts are sequential create/alter steps, so their resulting columns are shown together below. This is a snapshot of exported DDL, not a live database inspection. Treat the database engine as MySQL/InnoDB with `utf8mb4` where specified by the scripts.

Conventions: `NOT NULL` means required; `NULL` means optional. Defaults and enum choices are recorded where present. `AUTO_INCREMENT` IDs are generated by MySQL. `LONGBLOB` fields hold binary attachments/documents. Timestamps with `ON UPDATE CURRENT_TIMESTAMP` update automatically when a row changes.

## Relationship map

```text
organization_master (organization list; linked by organization name in application logic)

kss_student_scholarship 1 ── 0..1 kss_scholarship_approval
kss_student_scholarship 1 ── many kss_scholarship_audit (application logic; audit FK is not declared)

kss_csr_approval_letter 1 ── many kss_csr_work_order
kss_csr_work_order 1 ── many kss_csr_work_order_item
kss_csr_work_order 1 ── many kss_csr_invoice
kss_csr_approval_letter 1 ── many kss_csr_fund_request
kss_csr_fund_request 1 ── many kss_csr_fund_receipt (via nullable receipt.frl_id)
kss_csr_approval_letter 1 ── many kss_csr_fund_receipt (receipt.letter_id also remains required)
kss_csr_fund_request many ── many kss_csr_invoice (through kss_csr_frl_invoice;
                                                UNIQUE invoice_id means each invoice can be linked once)
kss_csr_invoice 1 ── 0..1 settling invoice (self-reference through proforma_id;
                                         UNIQUE proforma_id permits one tax invoice per proforma)
```

Foreign-key delete behavior is summarized under each table. The SQL does not define an explicit foreign key from scholarship audit rows to scholarship records, nor from scholarship records to `organization_master` or `users`; those associations are handled by application values rather than declared constraints in these exports.

## End-to-end workflows

### Scholarship
1. An application is stored in `kss_student_scholarship`; document bytes are stored in its BLOB columns.
2. Verification and decision/reimbursement data are stored in its optional one-to-one `kss_scholarship_approval` record.
3. Application changes can be written to `kss_scholarship_audit`.
4. `organization_master` supplies organization names; `users` supplies login/role records.

### CSR funding
1. Create an approved activity in `kss_csr_approval_letter`.
2. Create work orders and line items in `kss_csr_work_order` and `kss_csr_work_order_item`.
3. Record proforma or tax invoices in `kss_csr_invoice`. A tax invoice may point to the proforma it settles using `proforma_id`.
4. Create an FRL in `kss_csr_fund_request`; link claimed invoices in `kss_csr_frl_invoice` and set each invoice's `claim_amount`.
5. Record received money in `kss_csr_fund_receipt`, linked to both the approval letter and, where known, the FRL.

The meanings above describe stored relationships. Business rules such as validating amounts against approvals, invoice totals, or prior advances may also be enforced in Java code and are not guaranteed solely by the listed SQL constraints.
